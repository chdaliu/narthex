# Narthex — Agent Guide (English)

This document is for AI agents / developers working in the Narthex codebase: how to understand the architecture, reproduce the build, verify changes and follow the conventions.

## 1. What Narthex is

Narthex is a **super lightweight** local web dashboard: after entering a password, it launches and stops local apps (ComfyUI servers, opencode/mdBook/GitVelo/VS Code/VSCodium/WeTTY web) keyed by app type, with one-click start/stop, live status and memory, and one-click access to their web UIs. Core constraints:

- **Minimal footprint**: a single static Go binary with the frontend and assets embedded via `go:embed`; ~10 MB idle memory
- **Minimal dependencies**: only `golang.org/x/crypto` (argon2id); **any new third-party dependency must be justified in this document**
- **Keyed by kind**: each app type (`comfyui` / `opencode` / `mdbook` / `gitvelo` / `vscode` / `vscodium` / `wetty` / `emulatorjs`) has at most one card; `Kind` is the unique identity; **no paths, no directory search** — except the mdBook card, which stores the selected book project directory, and the EmulatorJS card, which stores the selected ROM file (see §7 kind semantics)
- **App detection at startup**: apps that are not installed are never shown (the `apps` field of `/api/meta` reports installed state); the EmulatorJS kind needs no binary — it is offered once `emulatorjs.dirs` is non-empty

## 2. Architecture and data flow

```
Browser (embedded web/*)
   │  HTTP + session cookie
   ▼
internal/server  routing + auth middleware + static files
   │
   ▼
internal/api    Service (mutex-protected State)
   │  ├─ auth: login rate limit → argon2id verify → HMAC session
   │  └─ procman.Backend interface (the ONLY exit for process operations):
   │        Manager: Start dispatches by kind and spawns the instance
   │        process (Setpgid process group)
   ▼
internal/store   atomic JSON writes: config.json / state.json
                 instance logs → logs/<cardID>.log
```

Key flows:

- **Create a card**: `api.HandleCreateCard` → kind is known → the app is installed (`err.appNotFound`) → the kind is not duplicated (`err.duplicateKind`); default name/icon per kind (ComfyUI→palette, opencode→terminal, mdbook→book-open, gitvelo→git-branch, vscode→code, vscodium→code, wetty→terminal); an mdBook card additionally requires `dir` to be one of the projects recognized under `mdbook.dirs` (`err.mdbookNoProject`)
- **Start a card**: `api.HandleStartCard` → `Backend.Start(kind, dir, id, hosts, noAuth)` (hosts = browser-side hosts from `s.browserHosts`: the request host plus the configured internal address; servers with origin checks derive their trusted origins from it; noAuth is true only for a gitvelo card with the proxy on, so its server skips its own login and stays on loopback); the comfyui code dir is resolved at start time by `procman.DetectComfyUIInstalls` and the desktop's shared model paths config (`--extra-model-paths-config`), shared/per-install input-output dirs (`--input-directory`/`--output-directory`) and extra launch args (e.g. `--enable-manager`) are passed through by `procman.comfyLaunchArgs`; the opencode/GitVelo/VS Code/VSCodium/WeTTY working dir is `os.UserHomeDir()`; the mdBook working dir is the project directory stored on the card and the emulatorjs working dir is the ROM's directory (a spawned narthex `emulator-serve` child) → spawn (cwd = the relevant dir, `Setpgid: true`, logs to `<LogDir>/<id>.log`) → record `pid/port/startedAt` in state; the opencode process carries its basic-auth password via the `OPENCODE_SERVER_PASSWORD` env var, the GitVelo process is launched as `gitvelo serve --no-auth --host 127.0.0.1 --port <n>` in proxy mode (direct mode: `gitvelo serve --host <gitvelo.hostname> --port <n>`), the VS Code/VSCodium process carries its connection token via `--connection-token`, the WeTTY process gets its SSH target via `--ssh-host`/`--ssh-port`/`--ssh-user` (no HTTP-layer secret; managed mode spawns a private loopback sshd first and points WeTTY at it) and its trusted origins via repeatable `--allowed-origin`
- **Status refresh**: the frontend polls `GET /api/cards` every 5 s; the server calls `Backend.Status(kind, pid, port)` per card (kill 0 + TCP health check + RSS)
- **Stop**: `Backend.Stop(pid)` → SIGTERM to the process group, then SIGKILL after a 5 s grace period
- **Session expiry / stale tabs**: API responses are `Cache-Control: no-store`; the frontend revalidates `GET /api/session` on focus/visibility/bfcache restore and drops to the login page with a `login.sessionExpired` notice when the session is invalid; the opencode and gitvelo gateway listeners stay bound for the whole serve lifetime, so a stale tab gets the login redirect (invalid session) or the localized "opencode/GitVelo is not running" page (upstream gone) instead of a connection-refused blank page
- **mdBook same-origin proxy**: the book is reverse-proxied at `/mdbook/` on the dashboard listener (see `internal/gateway/mdbook.go`) and the card "Open" URL is the relative path `/mdbook/`; `MdbookGatewayTarget` resolves the running mdBook card's loopback address per request, answering a localized "mdBook is not running" page when it is stopped, and `/__livereload` is proxied too for live reload. No extra port needs exposing: a single reverse proxy/tunnel reaches the book
- **EmulatorJS same-origin proxy**: the player is reverse-proxied at `/emulator/` (see `internal/gateway/emulatorjs.go`) and the card "Open" URL is the relative path `/emulator/` when the proxy is on; `EmulatorGatewayTarget` resolves the running child's loopback address per request (a localized "EmulatorJS is not running" page when stopped). With the proxy off the card opens the child's direct port
- **GitVelo gateway**: GitVelo's login is a cookie session narthex cannot inject, so the default (proxy on) runs the server with `--no-auth` on loopback and fronts it with a dedicated gateway listener (`gitvelo.gatewayPort`, default 26101; see `internal/gateway/gitvelo.go`) gated by the narthex session. With the proxy off the server keeps its own login on `gitvelo.hostname` and the card opens its direct port; changing the toggle requires the card to be stopped because it changes the spawn arguments (`err.gitveloProxyRunning`)
- **Restart recovery**: state.json persists pid/port; instances are lazily re-associated after a restart and dead processes show as "stopped"; when the desktop app is already running (single-instance handoff), `appProcessRunning` (pgrep) reports it as running
- **Password/username change**: `narthex passwd` and `narthex reset-auth` re-hash with argon2id and **rotate `sessionSecret`** (every issued session becomes invalid), re-**encrypting** the stored username with the new key (see `secretbox`); serve reads the config at startup, so restart serve after a CLI change; changing the account from the top-bar "Account" page (`/api/account`) updates memory and disk directly and takes effect immediately

## 4. Requirements

- Go ≥ 1.26 (`go.mod` declares `go 1.26`)
- At runtime: the managed apps (`Comfy Desktop.app` installed in `/Applications` or `~/Applications`, or pointed to via `NARTHEX_COMFY_APP_DIR`; the `opencode` CLI on PATH, or pointed to via `NARTHEX_OPENCODE_BIN`; the `mdbook` CLI on PATH + a non-empty `mdbook.dirs`, or pointed to via `NARTHEX_MDBOOK_BIN`; the `gitvelo` CLI on PATH, or pointed to via `NARTHEX_GITVELO_BIN`; the `code` CLI on PATH, or pointed to via `NARTHEX_VSCODE_BIN`; the `codium` CLI on PATH, or pointed to via `NARTHEX_VSCODIUM_BIN`; the `wetty` CLI on PATH **and its Node runtime**, or pointed to via `NARTHEX_WETTY_BIN`; WeTTY's managed sshd needs no system SSH server, only `/usr/sbin/sshd`); not needed for build or tests
- macOS (development) or Linux; test scripts need `bash`, `curl`, `python3`
- serve launched by launchd (`brew services` or the built-in autostart job) runs with only `/usr/bin:/bin:/usr/sbin:/sbin` on PATH; the CLI kinds (opencode/mdbook/gitvelo/vscode/vscodium/wetty) and the ComfyUI python resolve through `procman.lookPath`, which falls back to well-known Homebrew bin directories when PATH misses — no dependence on the user's shell PATH. Spawned children additionally get those existing dirs appended to their `PATH` by `procman.childPathEnv` (`spawn`), because lookPath's fallback does not help a CLI that shells out to its own interpreter (WeTTY's `#!/usr/bin/env node`)

## 5. Reproduction (from scratch to working)

```bash
git clone <repo> && cd Narthex
go mod tidy              # fetches golang.org/x/crypto only
make build               # → build/narthex (single binary, no other files needed)
./build/narthex setup      # interactive password → ~/.config/narthex/config.json
./build/narthex serve      # → http://127.0.0.1:9090
```

Non-interactive: `./build/narthex setup --random --force` (prints the random password); the login username defaults to `narthex` and can be set with `--username`.
Account changes: `./build/narthex passwd` or `reset-auth` (rotates sessionSecret; restart serve afterwards).
serve prints `detected apps: ...` at startup; only detected apps can be added as cards in the UI.

## 7. Conventions (must follow)

- **Dependency rule**: only `golang.org/x/crypto` (official) is allowed. Any new dependency must be justified in this section; prefer stdlib implementations (see the hand-rolled `internal/termios` echo-off input)
- **Comment discipline**: no decorative comments; comment only the "why"
- **State file format**: `Card` field changes in state.json are breaking — new fields must be `omitempty` or have backward-compatible defaults handled in `store.LoadState`; never rename existing JSON fields
- **API changes**: all `/api/*` endpoints (except login/session/logout) must stay behind auth; register new endpoints in the protected mux in `internal/server/server.go` and keep the frontend in sync
- **Concurrency**: every handler that reads/writes `Service.State` must hold `s.mu` first; process operations (Start/Stop) run under the lock to prevent concurrent start/stop of the same card
- **Single exit for process operations**: all start/stop/status calls must go through the `procman.Backend` interface; never call `os/exec` or the `procman` internals directly from the api/server layers
- **Account changes must rotate**: `passwd`/`reset-auth`/`/api/account` must rotate `sessionSecret` along with `passwordHash` and **re-encrypt** `usernameEnc` (the two are coupled, see `secretbox`); changing only the hash is a defect
- **Username is ciphertext-only**: never store the username in plaintext in the config; always `secretbox.Encrypt` for new/changed accounts and read via `resolveUsername`/`secretbox.Decrypt`; the username lives decrypted only in memory (`api.Service.Username`)
- **Settings semantics**: `POST /api/settings` applies fields one by one — empty `language`/`pageBackground` means "not set" (no change); `slogan` is a `*string` (`nil` = no change, `""` = hide, non-empty custom ≤80 chars); `internalAddress` is a `*string` (`nil` = no change, `""` = clear, custom ≤253 chars); `gatewayPort` is a `*int` (`nil` = no change, validated 1–65535 and ≠ the dashboard port; changing it rebinds the opencode gateway immediately via `restartGatewayLocked`); `gitveloGatewayPort` is the equivalent `*int` for the gitvelo gateway; a nil/unset `slogan` resolves to `i18n.T(lang, "slogan.default")` per the current language, and a customized slogan no longer follows language switches (see `api.sloganValue`)
- **Internal network address**: when `Config.InternalAddress` is set, card "Open" URLs (`api.instanceURL`) use it instead of the request host; the address may include a port (`net.SplitHostPort` decides: with a port it is used verbatim, otherwise the card port is appended); the frontend Settings input shows the current access host as its placeholder (`window.location.host`) and saves on a debounced input (see `web/app.js`)
- **i18n rule**: every user-visible string (CLI, API errors, frontend) must go through `i18n.T`/`t()`; hardcoded strings are a defect. The `internal/i18n` completeness test fails on any missing translation (all three languages must be present)
- **Upload safety**: `/api/uploads` accepts only jpg/png/webp, ≤15 MB, random hex filenames; the `/uploads/` static handler must reject path traversal and unknown extensions (see `server.uploadsHandler` and `api.UploadExt`)
- **Adding a language**: fill every key in the three `internal/i18n` maps → fill the three dicts in `web/i18n.js` → add the language to the `i18n.Parse` whitelist → add an option to the language dropdown in `index.html` → update both docs
- **Kind semantics**: cards are identified by `Kind` (`comfyui`/`opencode`/`mdbook`/`gitvelo`/`vscode`/`vscodium`/`wetty`/`emulatorjs`), one card per kind at most; creation requires the app to be installed (400 `err.appNotFound`) and the kind to be new (409 `err.duplicateKind`); cards **store no path** — the install directory is resolved at start time by the detection functions (**exceptions**: the mdBook card stores the chosen book project in `Card.Dir`, validated at creation against the projects detected under `mdbook.dirs`; the EmulatorJS card stores the chosen ROM file in `Card.Dir`, validated against the games detected under `emulatorjs.dirs`)
- **Reverse-proxy toggle**: the proxy-capable kinds (`mdbook`/`emulatorjs`/`opencode`/`gitvelo`) can opt out of the narthex proxy per card. `Card.DisableProxy` (omitempty; missing = proxy **on**, so existing behavior is unchanged) is toggled by `PATCH /api/cards/{id}` with `{"proxy":bool}` (`cardRequest.Proxy *bool`; `api.proxyCapable` gates it and other kinds ignore it). `api.instanceURL(reqHost, kind, port, proxy)` returns the same-origin path when `proxy` is true (`/mdbook/`, `/emulator/`, the opencode gateway port, or the gitvelo gateway port) and the app's direct `http://<host>:<port>/` otherwise. `view` computes `proxy := proxyCapable(kind) && !c.DisableProxy`. GitVelo is special: the toggle changes the spawn arguments (`--no-auth` on loopback vs its own login), so it is rejected with 409 while that card runs
- **EmulatorJS (process-less-looking but spawned)**: EmulatorJS ships no CLI/server, so narthex serves it itself: `procman.startEmulatorJS` re-execs the narthex binary (hidden `emulator-serve` subcommand → `internal/emulatorserver`, ROM/core/name/data resolved by `procman.EmulatorCoreFor`/`emulatorGameName`), so the card gets a **real** PID/port/health/memory like every other kind. `appInstalled` requires `Config.EmulatorJS.Dirs` non-empty; creation requires `dir` in `DetectEmulatorGames(emulatorjs.dirs)` (`err.emulatorNoGame`); the kind is proxied same-origin at `/emulator/` (`gateway.EmulatorHandler`) or opened on the child's direct port when the proxy is off; the player assets load from the CDN by default or from `emulatorjs.dataPath`. `DetectEmulatorServer` resolves `NARTHEX_EMULATOR_BIN` or `os.Executable()`. No COOP/COEP headers (the dashboard keeps working at the cost of threaded cores)
- **ComfyUI server launch**: go through `procman.startComfyUI` (spawn `<python> main.py --port <n> --listen <host>`, cwd = install code dir, Setpgid); `procman.comfyLaunchArgs` fills in the desktop-parity args from the matching `installations.json` record — shared model config `--extra-model-paths-config` (per-install `instance-model-paths/<id>.yaml`, falling back to `shared_model_paths.yaml`), `--input-directory`/`--output-directory` (from `settings.json`, or the record's fields when `useSharedInput/Output=false`) and the record's `launchArgs`; a code dir with no matching record gets no desktop args; `appInstalled` requires both `DetectComfyUIApp()` and `DetectComfyUIInstalls()` to be non-empty; the listen address and port range come from `Config.ComfyUI` (`0.0.0.0` by default for LAN access)
- **opencode web launch**: go through `procman.startOpencode` (spawn `opencode serve --port <n> --hostname <host>` on v2 / `opencode web --port <n> --hostname <host>` on v1 — the subcommand is picked from `opencode --version`, because v2 removed `web` — cwd = user home, Setpgid); `appInstalled` requires `DetectOpencode()` to be non-empty; **`OPENCODE_SERVER_PASSWORD` is mandatory** — the server binds `0.0.0.0`, and without a password it is unsecured on the LAN. The password is generated on first serve, persisted in `Config.Opencode.Password`, and surfaced on the card via `CardView.Password`. Browsers never talk to opencode directly: the card "Open" URL points at the narthex gateway (a second listener on the fixed `opencode.gatewayPort`, default 4399; a free port is used when it is occupied, gated by the narthex session cookie) which injects the basic-auth credentials server-side — this avoids both the native prompt and opencode's `crossorigin` asset bug that blanks the page under basic auth. The gateway listener is bound for the **whole serve lifetime** (`reconcileGateway`/`ReconcileGateway` at serve startup and on card changes), **not** only while opencode runs: when opencode is stopped the gateway answers a localized "opencode is not running" HTML page that redirects to the dashboard, and unauthenticated requests are redirected to the dashboard login, so a stale opencode tab never hits a connection-refused blank page (`api.Shutdown` releases the listener). `CardView.APIURL` still exposes the direct `http://<host>:<port>/` endpoint (also shown as the card's "API" row) so remote clients (`opencode attach`, the SDK) keep working against the password-protected port. The listen address and port range come from `Config.Opencode` (`0.0.0.0` / `[4300, 4499]` by default)
- **mdBook server launch**: go through `procman.startMdbook` (spawn `mdbook serve --port <n> --hostname <host>`, cwd = book project dir, Setpgid); `appInstalled` requires `DetectMdbook()` non-empty **and** a non-empty `Config.Mdbook.Dirs` — while the dirs list is empty the mdBook kind is hidden entirely; the card creation requires a `dir` in `DetectMdbookProjects(Config.Mdbook.Dirs)`; new books are created via `CreateMdbookProject` (`mdbook init --force --ignore none`, non-interactive) under one of the configured dirs only. The listen address and port range come from `Config.Mdbook` (`0.0.0.0` / `[4500, 4699]` by default). Browsers reach the book through the **same-origin proxy** (`gateway.MdbookHandler`, mounted at `/mdbook/` on the dashboard listener): the card "Open" URL is the relative path `/mdbook/` and `MdbookGatewayTarget` resolves the running card's loopback address per request (a localized "mdBook is not running" page when stopped); `/__livereload` is proxied too. No extra port needs exposing, so a single-port reverse proxy/tunnel reaches the book
- **GitVelo web launch**: go through `procman.startGitvelo`; `appInstalled` requires `DetectGitvelo()` to be non-empty. GitVelo's web login is a **cookie session**, not basic auth, so narthex cannot inject it like opencode's: with the proxy **on** (default) the child runs `gitvelo serve --no-auth --host 127.0.0.1 --port <n>` (port from `Config.Gitvelo.PortRange`, default [5400, 5599]) and the card "Open" URL points at the dedicated narthex gateway (`Config.Gitvelo.GatewayPort`, default 26101, bound for the whole serve lifetime by `reconcileGitveloGatewayLocked`; `GitveloHandler` gates it with the narthex session and strips the cookie). The loopback bind is mandatory: `--no-auth` must never be reachable from the network. With the proxy **off** the child runs `gitvelo serve --host <Config.Gitvelo.Hostname> --port <n>` with its own login and the card opens its direct port; `GitveloGatewayTarget` reports false in this mode so the gateway answers the stopped page. Because the toggle changes the spawn arguments, `HandlePatchCard` rejects it with 409 (`err.gitveloProxyRunning`) while the card is running. The card surfaces no credentials
- **VS Code web launch**: go through `procman.startVSCode` (spawn `code serve-web --host <h> --port <n> --connection-token <t> --server-data-dir <d> --accept-server-license-terms --disable-telemetry`, cwd = user home, Setpgid, child PATH shadowed with the no-open dir); `appInstalled` requires `DetectVSCode()` to be non-empty; **`--connection-token` is mandatory** — the server binds `0.0.0.0`, and without a token it is unsecured on the LAN. The token is generated on first serve, persisted in `Config.Vscode.ConnectionToken`, and surfaced on the card via `CardView.Password` (no username); the card's "Open" URL embeds it as `?tkn=` via `api.instanceURL`/`api.codeToken`, because the server answers 403 without the token (the browser sets the auth cookie on first load). `--server-data-dir` comes from `Config.Vscode.DataDir` (default `<config>/vscode-data`, `~/` expanded) and pins server-side state: browser *user* settings live in the browser (IndexedDB) and can be evicted (private windows, Safari ITP), so durable settings go to the server-side Machine settings; when `Config.Vscode.MachineSettingsFile` is set, its keys are seeded into `<data-dir>/data/Machine/settings.json` (missing keys only; Remote Settings edits win). Point `DataDir` at another server's dir (e.g. `~/.vscodium-server`) to share server-side state with a manually launched instance. The listen address and port range come from `Config.Vscode` (`0.0.0.0` / `[4700, 4899]` by default)
- **VSCodium web launch**: go through `procman.startVSCodium` (spawn `codium serve-web --host <h> --port <n> --connection-token <t> --server-data-dir <d> --accept-server-license-terms --disable-telemetry`, cwd = user home, Setpgid, child PATH shadowed with the no-open dir); `appInstalled` requires `DetectVSCodium()` to be non-empty; the token is generated on first serve, persisted in `Config.Vscodium.ConnectionToken`, and surfaced on the card via `CardView.Password` (no username); its "Open" URL carries the token the same way. It is a fully independent kind from VS Code (own config, own token, own port pick, own `--server-data-dir` from `Config.Vscodium.DataDir`, own `Config.Vscodium.MachineSettingsFile`), so both can run at the same time. Listen address and port range come from `Config.Vscodium` (`0.0.0.0` / `[4700, 4899]` by default, a free port is picked at start)
- **WeTTY terminal launch**: go through `procman.startWetty` (spawn `wetty --port <n> --host <h> [--ssh-host <h>] [--ssh-port <n>] [--ssh-user <u>] --allowed-origin <o>...`, cwd = user home, Setpgid); `appInstalled` requires `DetectWetty()` to be non-empty. **Managed SSH mode is the default** (`Config.Wetty.SSHMode`, normalized to `managed` when absent; overridden to `system` when the old config sets an explicit `sshPort`): when `sshHost` is loopback (`localhost`/`127.0.0.1`/`::1`/empty), narthex writes `<WettySSHDir>/sshd_config` + an ed25519 host key, spawns `/usr/sbin/sshd -D -e -f <cfg> -p <port>` from `Config.Wetty.SSHPortRange` (default [5300, 5399]) on `127.0.0.1` only, waits for the port, then starts WeTTY with `--ssh-host 127.0.0.1 --ssh-port <port> --ssh-user <narthex user>`. The generated config uses PAM password auth (`UsePAM yes`), `AllowUsers <narthex user>`, `PubkeyAuthentication no`, `PermitRootLogin no` and disables X11/agent/TCP/stream-local forwarding and tunnels; the sshd is non-root, so it can only ever authenticate the narthex account (`sshUser` must match it). `state.json` (`wettyPid`/`sshdPid`/`sshPort`) plus the wetty exit callback (`spawn` onExit) and `Manager.Stop` kill the sidecar; a later start reaps a stale one after verifying the pid's command line references the generated config (PID-reuse guard). A non-loopback `sshHost` or `sshMode=system` keeps the configured SSH target (the old behavior, including `sshHost`/`sshPort`/`sshUser`). Managed mode is designed for macOS: most Linux distributions refuse PAM password auth from a non-root sshd, so use `system` there. WeTTY has **no HTTP-layer auth**: the browser authenticates with the private sshd (managed) or the configured SSH account (system); the SSH target is never taken from URL parameters (`--allow-remote-hosts`/`--allow-remote-command` stay off). The card surfaces no credentials. Listen address and port range come from `Config.Wetty` (`0.0.0.0` / `[4900, 5099]` by default; LAN access is unchanged — only the SSH hop is loopback). WeTTY >= 4 refuses to start without a trusted origin: `startWetty` derives the repeatable origins from `wettyOrigins` (the page lives on wetty's own port, so `http://<browser host>:<wetty port>`), covering localhost/127.0.0.1 plus the `Backend.Start` hosts (request host and internal address); if the card is later opened via a different hostname, the origin check fails — restart the card from that host
- **EmulatorJS launch**: go through `procman.startEmulatorJS` (re-exec the narthex binary as `emulator-serve --rom <file> --core <core> --name <name> --host <h> --port <n> [--data <dir>] [--cdn <ver>]`, cwd = ROM dir, Setpgid, `NARTHEX_EMULATOR_BIN` override for tests); `appInstalled` requires a non-empty `Config.EmulatorJS.Dirs`; card creation requires `dir` in `DetectEmulatorGames(emulatorjs.dirs)` (`err.emulatorNoGame`); the ROM extension is the sole core selector (`EmulatorCoreFor`; archives resolve via the inner extension). EmulatorJS ships no binary, so narthex serves it itself (`internal/emulatorserver`, run by the hidden `cmdEmulatorServe`) — the card still gets a real PID/port/health/memory. The player is proxied same-origin at `/emulator/` by default or opened on the child's direct port when the proxy is off; assets come from the CDN or `emulatorjs.dataPath`. No COOP/COEP headers (threaded cores unavailable, documented). Listen address and port range come from `Config.EmulatorJS` (`0.0.0.0` / `[5100, 5299]` by default)
- **Port rules**: comfyui ports are probed from `comfyui.portRange` (default [4100, 4299]); opencode ports from `opencode.portRange` (default [4300, 4499]); mdbook ports from `mdbook.portRange` (default [4500, 4699]); gitvelo ports from `gitvelo.portRange` (default [5400, 5599]) and its gateway from `gitvelo.gatewayPort` (default 26101); vscode ports from `vscode.portRange` (default [4700, 4899]); vscodium ports from `vscodium.portRange` (default [4700, 4899]); wetty ports from `wetty.portRange` (default [4900, 5099]); the managed WeTTY sshd port from `wetty.sshPortRange` (default [5300, 5399], loopback only, alive only while the card runs); emulatorjs ports from `emulatorjs.portRange` (default [5100, 5299]); never hardcode ports. Health checks always dial `127.0.0.1`

## 8. Common extension points

- **Add a managed app**: add a detection function (`detectAppBundle`) and a launch branch in `procman`, a kind constant in `store`, default name/icon in `api.kindLabel`/`defaultIcon`, and extend the frontend `ALL_KINDS` list plus the `modal.kind<kind>Desc` copy (following the §7 kind semantics). For a proxy-capable kind also add it to `api.proxyCapable` and the frontend `PROXY_KINDS`
- **Add a same-origin proxied app**: follow `internal/gateway/mdbook.go` (prefix constant + `*Handler` with session gate, prefix strip and `writeStoppedPage`) and mount it in `internal/server/server.go`; add an `*GatewayTarget` resolver on `Service` and a `store.Kind` case in `api.instanceURL`. For an app with root-absolute paths (or its own login switch), follow the dedicated-listener pattern instead: `internal/gateway/gitvelo.go` plus `Server.GitveloGatewayHandler`, `Service.GitveloGatewayPort`/`reconcileGitveloGatewayLocked`, and `cmd/narthex` wiring/printing
- **Add assets**: drop files into `web/assets/` and rebuild (embed picks them up automatically); the `/api/meta` endpoint lists icons/backgrounds at runtime
- **Docs**: update the root `README.md` (English) and `docs/README.zh-CN.md` (Chinese) in pairs; `docs/agents/AGENTS.*` likewise. The root `AGENTS.md` is a pointer only

## 9. Known limitations

- Only instances started by Narthex are managed; services started externally on the same port are not in card state
- Memory is the process RSS, not the sum of child processes
- Sessions are stateless signed cookies; a signature stays valid up to 30 days after logout by default (configurable via `sessionTTLHours`; accepted tradeoff — rotate `sessionSecret` if immediate invalidation is needed)
- A password change requires restarting `narthex serve` (sessionSecret/passwordHash are read into memory at startup); account changes from the UI (`/api/account`) take effect immediately without a restart
- The ComfyUI server is started directly via `python main.py` and is independent of the ComfyUI Desktop window; if the user runs the desktop app too, its embedded server (8000–9000 range) is not managed by Narthex
